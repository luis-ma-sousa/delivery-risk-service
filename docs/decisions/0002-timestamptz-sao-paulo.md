# 0002 — Timezone-aware timestamps in America/Sao_Paulo

**Status:** Accepted
**Date:** 2026-08-21

## Context

All timestamps in the source CSVs are naive: no offset, no zone. They are
generated by Olist's systems rather than by each customer's local clock, so a
single timezone applies to all of them regardless of where the customer is.
Brazil has four timezones; the relevant one is `America/Sao_Paulo`.

The data spans 2016-09-04 to 2018-10-17. Brazil observed daylight saving time
throughout that period, giving four transitions inside the range:

| date       | direction      | timestamps that day |
|------------|----------------|---------------------|
| 2016-10-16 | spring forward | 10                  |
| 2017-02-19 | fall back      | 73                  |
| 2017-10-15 | spring forward | 221                 |
| 2018-02-18 | fall back      | 419                 |

On a spring-forward date one local hour does not exist; on a fall-back date one
local hour occurs twice and is ambiguous.

## Decision

Store every timestamp as `timestamptz`, converting from naive local time in
`America/Sao_Paulo` at ingestion.

Ambiguous times resolve to the earlier of the two possible instants; times that
do not exist shift forward by the length of the gap. Both policies are set
explicitly in the ingestion code rather than left to library defaults.

## Alternatives considered

**Store naive `timestamp`.** Every quantity the model uses is a difference
between two timestamps from the same source, and differences are unaffected by
timezone. Naive storage would produce identical model results with none of the
DST handling. Rejected as a deliberate trade: choosing the DST policy is a
decision this project exists to practise, and doing it against historical data
is cheaper than discovering it in production.

**Store UTC without zone information.** Rejected: it discards the local wall
clock, so day-of-week and hour-of-day features would be computed in the wrong
frame.

## Consequences

- Ingestion carries roughly ten lines of explicit conversion logic and a
  documented policy for two edge cases.
- A handful of timestamps on the four transition dates are shifted by up to one
  hour relative to their source value. This is accepted; the alternative is a
  value that has no valid instant.
- Day-of-week and hour-of-day features are computed in local time, which is the
  frame in which the logistics operation actually runs.
